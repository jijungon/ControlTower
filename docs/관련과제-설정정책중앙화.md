# 설정·정책 중앙화 과제 — 메모 해석 정리 (임시 초안)

> **Control Tower와 별개 트랙**인 인프라 과제. Control Tower(운영 관리·관측 도구)가
> 서버의 설정 파일을 관측/배포한다면, 이 과제는 서비스가 런타임에 읽는 설정·시크릿·
> ratelimit **저장소 선정·HA 설계**를 다룬다.
> 접점: Control Tower의 버전/패키지 인벤토리 → 라이선스 노출(Redis/Vault/Consul) 조사에
> 재활용. 통합 여부는 추후 결정. (저장 2026-09-10)

- 작성일: 2026-09-10
- 상태: **해석 단계 초안** — 지시자 확인 전. `⬜` 항목은 채워 넣을 것.
- 용도: 상세 설명을 다시 작성할 때 뼈대로 쓰는 임시 문서.

## 0. 원본 메모 (원문 보존)

```
redis 개발 진형이 이상해짐(연동, api, web ui) -> 약점을 보완하자

vault cluster -> openbaw
redis (멀티 마스터, slave) -> 프록시 lb -> health check 는 -> 샤딩 /// redis 의 대체제 //// consul
성능 <<<<<<<<<<<<<<<<<<<<<<< 이점
매번 질의                                               설정파일

설정을 중앙화 하자 설정파일 / 서버당 x, 서비스당 ratelimit
kong (api gateway - redis)
```

## 1. 한 줄 주제

> **서버마다 흩어진 설정·정책을 서비스 단위로 중앙화한다. 중앙 저장소는 라이선스 리스크 없는 스택으로 고르고(Valkey/Consul/OpenBao), SPOF가 되지 않게 HA로 설계하며, "매번 질의는 느리다"는 반론은 이점 크기 + 하이브리드 구성으로 방어한다.**

- **상위 주제(WHAT)**: 설정·정책의 중앙화 — 운영 단위를 "서버당" → "서비스당"으로 전환
- **대표 유스케이스(WHY)**: 서비스당 ratelimit — 서버당 설정으로는 서비스 전체 총량 제어가 원천적으로 불가능
- 나머지 메모는 전부 **HOW**(저장소 선정, HA 설계)와 **제약조건**(라이선스 리스크), **예상 반론**(성능)

## 2. 전체 구조 — 한 프로젝트로 묶기

```
설정·정책의 중앙화 (서버 단위 → 서비스 단위)
│
├─ WHY: 대표 유스케이스 — 서비스당 ratelimit
│    └─ Kong(api gateway) + redis policy = 서비스 전체가 공유하는 카운터
│
├─ HOW①: 중앙 저장소를 뭘로 할 것인가   ← "redis 대체제 /// consul" 줄
│    ├─ 제약: Redis 생태계 리스크(연동·api·web ui) → Valkey 등 대체제 검토
│    ├─ 설정 저장 용도라면 Consul KV도 후보
│    └─ 시크릿 축은 Vault → OpenBao (같은 라이선스 리스크 대응)
│
├─ HOW②: 중앙 저장소의 HA   ← 중앙화의 전제조건 (중앙이 SPOF면 전체 장애)
│    └─ 멀티마스터/slave → 프록시 LB → 헬스체크 → 샤딩
│
└─ 예상 반론: 성능 — "매번 질의 vs 설정파일"
     └─ 성능 손해 <<< 중앙화 이점 (+설정은 파일 렌더링 하이브리드로 성능 회수)
```

## 3. 메모 해독 (줄별)

- **"redis 개발 진영이 이상해짐(연동, api, web ui) → 약점을 보완하자"**
  2024년 Redis 라이선스 전환(BSD → RSALv2/SSPLv1, 2025년 Redis 8부터 AGPL 추가) 이후 클라이언트 라이브러리 거버넌스(연동), API/모듈 정책, RedisInsight(웹 UI) 등 생태계가 Redis사(社) 주도로 재편된 상황. → Redis 의존 리스크 평가 + 보완책 마련.

- **"vault cluster → openbaw"**
  OpenBao 오타. HashiCorp가 BUSL로 라이선스를 바꾼 뒤 Linux Foundation이 Vault를 포크한 프로젝트. 기존 Vault 클러스터의 OpenBao 전환 검토/PoC. Redis 건과 정확히 같은 동기(라이선스 리스크 → 오픈 포크로 이동).

- **"redis(멀티 마스터, slave) → 프록시 lb → health check → 샤딩"**
  Redis 계열을 유지할 경우의 HA 설계: 토폴로지(멀티마스터 or 마스터·레플리카), 앞단 프록시 LB(HAProxy/Envoy 류), 헬스체크 주체(Sentinel? 프록시? Consul?), 규모 확장 시 샤딩(Cluster).

- **"redis 의 대체제 /// consul"**
  대체 후보: **Valkey**(Linux Foundation 포크, 최유력), KeyDB(진짜 멀티마스터 지원, 다만 개발 활동 뜸), Dragonfly(BSL이라 라이선스 관점에선 탈락 사유), Garnet(MS, MIT) 등. Consul은 Redis의 경쟁 대체제가 아니라 "설정 저장" 역할을 분리해 가는 후보(→ 5번 참고).

- **"성능 <<< 이점 / 매번 질의 vs 설정파일"**
  중앙 저장소에 매 요청 질의하는 방식과 로컬 설정파일 방식의 트레이드오프. 결론 방향: 중앙화 이점이 훨씬 크고, 설정은 consul-template/envconsul 식 하이브리드(중앙 값 변경 시에만 로컬 파일로 렌더링)로 성능 손실을 회수. 다음 줄의 "설정을 중앙화 하자 **설정파일**"이 이 결론(중앙 관리 + 파일로 배포)을 가리키는 것으로 보임.

- **"서버당 x, 서비스당 ratelimit / kong(api gateway - redis)"**
  Kong rate-limiting 플러그인의 정책 구분이 정확히 이것: `local` = 노드별 카운터(서버당), `redis` = 공유 카운터(서비스당). Kong을 쓰면 어차피 Redis(호환 저장소)가 필요 → 위의 Redis HA/대체제 문제와 다시 연결됨. 메모 전체가 이렇게 맞물림.

## 4. 과제 분해 (4개)

1. **Vault → OpenBao 전환 검토** — API/스토리지 호환성, 마이그레이션 경로, 클러스터 구성
2. **Redis 대체제 비교 + HA 아키텍처 설계** — Valkey/KeyDB 등 비교표, 프록시 LB + 헬스체크 + 샤딩 구성안
3. **설정 중앙화 설계** — Consul KV(또는 etcd) 기반, "매번 질의 vs 파일 렌더링" 트레이드오프 정리
4. **Kong 기반 서비스 단위 rate limit** — redis policy 백엔드, 게이트웨이 설정도 중앙 관리

## 5. 핵심 설계 포인트 — 중앙 저장소 "자리"는 두 개

| 자리 | 워크로드 특성 | 후보 |
|---|---|---|
| 상태 저장 (ratelimit 카운터) | 초당 수천 R/W, Redis 프로토콜 필요 | Redis / Valkey |
| 설정 저장 (설정값) | 가끔 읽음, watch/파일 렌더링 가능 | Consul KV, etcd |

- Consul은 Redis의 경쟁 대체제라기보다 **설정 저장 역할을 분리해 가져가는 그림** — 메모의 "매번 질의 vs 설정파일" 줄과 대응
- ⚠️ 주의: **Consul도 BUSL**(HashiCorp). Vault를 라이선스 때문에 버리면서 Consul을 신규 도입하는 건 논리적 충돌 — etcd 등 대안도 비교 테이블에 올릴 것

## 6. 예상 산출물

- 비교/검토 보고서 + 아키텍처 다이어그램 + (방향 확정 시) PoC
- 제목 예: **"설정·정책의 서비스 단위 중앙화 — 저장소 선정과 HA 설계"**
- 목차 초안: 배경(라이선스 지각변동 + 서버 단위 설정의 한계) → 목표 → 유스케이스(Kong ratelimit) → 저장소 선정 비교 → HA 아키텍처 → 성능 트레이드오프 → PoC 로드맵

## 7. 채워야 할 것 (⬜)

상세 설명 작성 시 포함하면 좋은 것:

- ⬜ **현재 상태**: Redis/Vault/Kong 중 실제 운영 중인 것, 그걸 쓰는 서비스 목록
- ⬜ **산출물 범위**: 조사·비교 보고서까지 vs PoC 구축까지, 기한
- ⬜ **결정된 것 vs 열린 것**: 예) "Kong 확정, 저장소 미정"

지시자에게 확인할 질문:

- ⬜ Kong이 이미 운영 중인지, 도입 검토 단계인지
- ⬜ Consul의 역할 범위 — KV만인지, 서비스 디스커버리/헬스체크까지인지 (+ BUSL 이슈를 어떻게 볼지)
- ⬜ "멀티 마스터"가 진짜 active-active 요구인지, HA 구성의 통칭인지
- ⬜ 성능 요건 수치 — 설정 조회 지연 허용치, ratelimit 카운터 예상 QPS

## 9. Control Tower와의 접점 (2026-09-10 추가)

- **라이선스 노출 조사 = Control Tower 인벤토리의 부산물**: "어느 서버·서비스가 Redis(SSPL)·
  Vault(BUSL)·Consul(BUSL)을 쓰는가"는 Control Tower의 버전/패키지 인벤토리로 바로 뽑힌다
  → 이 과제 §7의 "현재 상태(운영 중인 것 + 사용 서비스 목록)" 채우기에 재활용.
- **설정이 파일→중앙 저장소로 이동하면** Control Tower의 conf 관리 대상 범위가 달라진다
  (파일 렌더링 하이브리드면 파일은 여전히 관측 대상; 순수 런타임 질의면 관측 포인트가 저장소로 이동).
- 통합(같은 제품으로 묶기) 여부는 이 과제 방향이 잡힌 뒤 재검토.
